# EX-07 owner setup room

The setup room uses the merged Passport and setup APIs for the selected business. It allows an owner to rediscover a saved setup after signing in, prepare a Gmail handoff, select an existing Gmail account subject to server checks, confirm business facts, review an allowlisted Shopify currency suggestion and record or revoke field-specific sharing consent. A connection, saved profile or consent is not a signed action policy or proof of an external effect. The browser retains only random idempotency keys in session storage; Passport values and preview tokens stay in memory and are not placed in URLs or analytics. If a setup response is lost, the pending key supports a labelled recovery after a reload. If session storage is unavailable, the owner is prompted to check saved setups before starting another.

Owners can also correct the canonical business name, country and time zone with a version check. Changing a fact makes its earlier confirmation stale and invalidates dependent sharing previews and consent, so the owner can review the updated information.

A missing Google OAuth configuration stays visible with a link to review or cancel the current handoff. The owner can recover a previously saved setup after sign-in, and a declined provider return does not erase it. The server checks current identity, scopes and health before an existing account can be reused; a stale or revoked account requires action. A completed external effect is never inferred from this screen.

For active setups, the client records help openings and bounded estimates of foreground interaction time. Time counts only while the page is focused and visible, with an idle cutoff; interrupted or failed uploads can undercount. These measurements are explicitly labelled `client_estimated`, are limited to a type and optional integer seconds, and cannot include entered field values. They use the existing tenant audit retention and export boundary. Existing Passport update audit events list field names without values and can help identify repeated edits, but do not measure comprehension. No setup-completion or comprehension success is inferred from clicks; those outcomes require defined evidence and a supervised study.

Desktop and mobile tests use a real local API and PostgreSQL, file-only verification mail and no Google credentials. They cover a synthetic profile, setup preparation, a deliberately dropped response and idempotent retry, data-sharing review and revocation, keyboard access to help, refresh, sign-out/sign-in recovery, business switching, and a simulated declined-provider return. Provider doubles and simulated redirects are not live OAuth evidence. Existing-account reuse is enforced and exercised in backend tests; live provider redirect, owner comprehension, broader provider support, and a complete end-to-end workflow remain outstanding.
