# EX-06 identity contract: preparation

This is a schema and interface preparation, not a working Google sign-in. No login route, provider configuration or Gmail grant is added by this slice. The first assistant-host proof still needs an authorized reachable HTTPS environment; live Google acceptance needs a configured identity client and dated evidence.

An external identity link belongs to the existing canonical Gluons user and is keyed by issuer plus immutable subject. The unique subject constraint includes revoked links so another account cannot claim a formerly linked subject. One user can have at most one record per issuer; re-linking a revoked identity must verify both the same Gluons user and the same provider subject. Email alone is never sufficient to link an existing user.

A browser-bound intent holds only hashes of random state, browser binding and nonce; a PKCE verifier must be sealed with the existing global vault before storage. Login intents have no user or session; linking intents require both. A future callback must atomically consume an unexpired intent once, validate the browser binding, issuer, audience, signature, nonce, token lifetime and PKCE code exchange, and recheck the linking session and MFA state. A second callback or a callback from a different browser must fail. An optional outer authorization request ID is a reference to an existing, independently validated assistant OAuth request, not a redirect URL or a grant.

The records are global user-security data, like existing users and identity sessions; they do not carry a tenant ID and cannot create or select a business. Forced row security limits link reads to the current user or a transaction-bound issuer and subject, and link writes to the current user. The future service may set issuer and subject only after provider verification. Intent access requires both the transaction-bound state and browser hashes; a separate transaction-local cleanup context permits access only to expired intents. Schema grants allow the identity service to read, create and update links; intent deletion is allowed for expiry cleanup. User and session foreign keys cascade on deletion. A future service must implement expiry cleanup and include linked identities in the applicable account export/deletion path before enabling sign-in. Unlinking must not remove the last usable authentication method or bypass MFA/recovery.

The future authorization request must request identity scopes only. Google sign-in and Gmail connector consent remain separate. An ID token cannot be used as a Gluons or MCP access token. Missing configuration leaves the feature unavailable. Existing email/password, MFA, session and tenant boundaries remain authoritative.

Google's [OpenID Connect guidance](https://developers.google.com/identity/openid-connect/openid-connect) describes state, nonce and server-side token validation; its [ID-token verification guide](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) identifies the stable subject as the account key. These references were checked November 10, 2026; actual provider behavior is not verified by the schema or local tests.

On November 10, local PostgreSQL tests exercised uniqueness, subject-only read access, denied cross-user reads and writes, browser-bound intent access and expired-only cleanup visibility, alongside the existing identity and assistant OAuth tests. A fresh isolated database passed Alembic drift check, downgrade to base and upgrade to head. The first migration-audit harness attempt failed before running the check because it called the helper on the database object; the corrected retry passed. These checks do not validate a Google sign-in or hosted assistant.
