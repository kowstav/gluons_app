# EX-08 readiness projection

The launch plan and evidence responses expose one read-only readiness projection. The owner launch screen displays it, and the assistant plan tool returns the same projection. The existing Shopify observation endpoint also returns that projection; its provider response is an observation, not permission or an independent launch decision. An observed test-order payment is not treated as a plan-verified checkout.

The current implementation can establish that an internal plan exists and that its bound Shopify connection is owner-confirmed, connected, linked to the plan, and checked within 24 hours. A missing, expired, disconnected or reconfirmed connection degrades the projection without erasing earlier evidence. The 24-hour recheck threshold follows the existing setup and Passport connection checks; it is an application policy, not a guarantee about the provider's state. Sandbox connection evidence is labelled sandbox and cannot establish production launch.

Catalog completeness, payment eligibility, tax and shipping, a plan-bound test checkout, a current approved publication manifest, publication completeness and operational/dispatch readiness remain blocked. Existing historical provider observations and individual action receipts do not establish the complete current plan, manifest, resource and version linkage required to promote these checks. They remain visible as history. This is a conservative initial projection, not proof of a production launch or completion of all EX-08 acceptance criteria. Future evidence contracts and stage orchestration must establish those links before the remaining checks can become verified.

New plan-scoped catalog and fulfillment actions reserve an append-only intent before gateway execution. The intent binds a hashed action key and normalized payload to the plan's business details, automation and confirmed store identity. A receipt can be attached only when its action, payload, automation, connection, environment and current plan/store context match that intent and the gateway recorded a successful readback. An existing unbound receipt cannot be retroactively assigned to a different plan; previously recorded history is retained. An individual matching receipt still does not prove a complete manifest or launch.

The projection can display individual matching provider readbacks from the last 24 hours when the bound store remains current and has the needed read scopes. Each item retains its source, environment, observation time, resource and receipt. The item disappears from current readiness if the plan or store context changes, access is revoked, scopes are lost or its readback ages out; historical evidence remains. A sandbox readback remains sandbox evidence. Even a verified Shopify fulfillment record does not establish physical dispatch or delivery.

If a provider action has already been verified but its plan evidence cannot be attached, the action result remains verified and carries a reconciliation warning. Retrying with the same plan-bound key uses the durable gateway receipt rather than repeating the provider write, provided the plan and store context still match.

The provider observation endpoint performs its live identity, payment and order reads outside the tenant transaction, then rejects the observation if the plan or connection changed. Credential renewal retains its existing transaction and connection lock because refresh tokens require serialized rotation. The observation and read-only projection are distinct. Tests use local PostgreSQL and provider doubles; no real Shopify account, checkout, publication, payment or delivery was exercised.
